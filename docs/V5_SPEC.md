# ТЗ v5: API для интеграций, шаблоны, Telegram, товары из чеков

Статус: **проект**, реализация не начата. Документ на русском, как и остальные в `docs/`.
Основа: v4 ([V4_SPEC.md](V4_SPEC.md)), группы и роли из [V2_SPEC.md](V2_SPEC.md).

## 1. Цели и принципы

- Приложением можно пользоваться не только из браузера: стабильный API с токенами для Home Assistant и скриптов.
- Частые траты добавляются одним касанием, **без перегрузки формы «Добавить»**.
- Приложение само сообщает о важном (лимиты, сбои) в Telegram.
- Позиции чеков складываются в общие «товары», чтобы по ним можно было считать аналитику.
- Обычный участник не видит новых сложных настроек, всё необязательное спрятано. Правила из `CLAUDE.md` действуют как раньше.

Этапы выкладываются по отдельности, каждый полезен сам по себе (порядок в разделе 7).

## 2. Решения владельца

| Вопрос                | Решение                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- |
| Telegram              | Один бот на установку                                                                         |
| Home Assistant        | Только REST (MQTT не нужен)                                                                   |
| Шаблоны               | И личные, и групповые; пользователь может делиться своими, скрывать групповые (все или часть) |

## 3. API и токены доступа (этап 1)

**Токены.** Личные, у каждого имя, область (`read` или `write`), срок (необязательно), можно отозвать.

- Формат `et_` + 32 случайных байта в base64url. Показывается **один раз** при создании. В базе только SHA-256, префикс (первые 8 знаков) для опознания и `last_used_at`.
- Передаётся заголовком `Authorization: Bearer …`, никогда в URL. Не попадает в логи.
- Токен действует от имени владельца и **не шире его прав** (группа, доступ к картам, роль). Область `read` не пишет.
- Токены создаются и отзываются только из сессии с cookie (токеном токен не выпустить). Сброс пароля отзывает все токены пользователя.
- Ограничение частоты запросов по токену. Неверный токен логируется без значения.

**Стабильный публичный слой `/api/v1`.** Внутренние маршруты `/api/*` остаются как есть и могут меняться, публичные описаны в OpenAPI (`GET /api/v1/openapi.json`) и меняются только с новой версией.

| Метод и путь                       | Что делает                                                                      | Область |
| ---------------------------------- | ------------------------------------------------------------------------------- | ------- |
| `GET /api/v1/summary?period=month` | Потрачено, число операций, расход в день, остаток по лимитам, в валюте на выбор | read    |
| `GET /api/v1/budgets`              | Лимиты по категориям: потрачено, лимит, остаток, процент                        | read    |
| `GET /api/v1/expenses?limit=`      | Последние операции                                                              | read    |
| `POST /api/v1/expenses`            | Добавить расход (с ключом идемпотентности)                                      | write   |
| `GET /api/v1/templates`            | Доступные пользователю шаблоны                                                  | read    |
| `POST /api/v1/templates/:id/apply` | Создать расход по шаблону (необязательно: `amount`, `date`)                     | write   |

**Интерфейс.** Настройки → «Доступ по API»: список токенов (имя, префикс, область, последний вызов), «Создать токен» (показать один раз с кнопкой «Копировать»), «Отозвать». Блок виден всем, но свёрнут; обычному участнику ничего лишнего не показывается.

**Документация.** `docs/HOME_ASSISTANT.md`: готовые примеры `rest` sensor (за месяц, остаток по категории) и `rest_command` (добавить расход, применить шаблон) для `configuration.yaml`.

## 4. Шаблоны быстрых действий (этап 2)

**Шаблон:** название кнопки, необязательный эмодзи, категория, карта (необязательно: тогда «моя карта по умолчанию»), название расхода, сумма и валюта (необязательно). Область: **личный** или **групповой**. Дата расхода всегда «сегодня» по часовому поясу пользователя (`request.user.timezone`).

- **Кто что делает.** Групповые шаблоны создаёт, включает и упорядочивает **владелец группы**; менять и удалять групповой шаблон могут владелец и его **автор** (тот, кто им поделился). Участник шаблон группе не публикует, он его **предлагает**: «Предложить группе» в меню личного шаблона создаёт отдельную групповую копию в статусе «предложение» (`status = 'proposed'`, ссылка `origin_id` на личный шаблон). Группа её не видит и не использует, пока владелец не нажмёт «Включить для группы» (может перед этим изменить или «Отклонить»). Автор видит своё предложение и может его **отозвать**, пока оно ждёт.
- **После включения** групповой шаблон живёт отдельно: владелец меняет только его, личный шаблон автора остаётся его собственным и не затрагивается. Автор может изменить или удалить свой групповой шаблон (правка видна всей группе, поэтому перед публикацией показывается подтверждение), включить предложение и менять порядок групповых может только владелец. На один личный шаблон приходится одна копия в группе (повторно предложить можно после отзыва или отклонения). Владелец группы делится своим личным шаблоном без предложения: «Опубликовать в группе» сразу создаёт включённую копию.
- **Скрытие.** Каждый пользователь скрывает включённые групповые шаблоны для себя: по одному или все сразу (личная настройка). Скрытие не влияет на других.
- **Карта.** Если у пользователя нет права добавлять на карту из шаблона (доступ снят, карта архивная), берётся его карта по умолчанию.
- **Сумма и валюта.** Сумма хранится вместе со своей валютой и создаёт расход в ней, как это делает форма «Добавить». Смена карты шаблона не пересчитывает сумму.
- **Порядок.** У каждого пользователя **свой**: любой шаблон (и групповой, и личный) перетаскивается куда угодно, в том числе личный выше группового (таблица `template_order`). По умолчанию, пока пользователь ничего не расставлял, сверху **групповые** (в порядке владельца, `PUT /api/templates/group-order`), затем личные. У того, кто расставил порядок сам, новый групповой шаблон встаёт наверх, новый личный в конец. Автосортировки по частоте нет. В настройках видно, что показывается над формой (первые три), что только в списке «Все» и что не показывается.
- **Таблицы:** `expense_templates` (группа, автор, область, статус, `origin_id`, поля, порядок, архив), `template_hidden` (пользователь, шаблон). «Скрыть все групповые» и «полоска над формой» это предпочтения `templates.hideGroup` и `templates.strip` (список ключей в `preferences.schema.ts` и `frontend/.../preferences.ts` должен совпасть). Шаблоны не стираются физически: удаление это архив.

### UI: вход в форму «Добавить» (решение: гибрид)

В поля формы ничего не добавляется. Над полями, под заголовком «Добавить расход», одна строка:

```
[Кофе 1 200] [Такси 1 500] [Продукты] [⚡ Все]
```

1. **Чипы.** До трёх первых доступных шаблонов (сначала групповые: у них приоритет, затем личные, каждые в своём порядке), у шаблона с суммой она написана на чипе. Строка не прокручивается и не переносится: что не влезло, находится в «Все».
2. **«⚡ Все»** (чип с пунктирной рамкой) открывает нижнюю панель «Быстрые траты»: разделы «Мои» и «Группа», в строке название, категория и сумма (или «сумма?»).
3. **Строки нет совсем**, если у пользователя нет доступных шаблонов или он отключил полоску (Настройки → Шаблоны → «Полоска над формой»). Если полоска отключена, но шаблоны есть, остаётся только маленькая кнопка ⚡ в заголовке карточки формы, которая открывает ту же панель.
4. Пока `templates.strip` не менялся, он включён. Участник без шаблонов не видит ничего нового (правило из `frontend/CLAUDE.md`).

**Нажатие на шаблон:**

| Случай                                 | Поведение                                                                                                                                       |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Сумма задана                           | Расход создаётся сразу (с ключом идемпотентности), тост «Добавлено · название · сумма · Отменить» на 6 секунд. «Отменить» мягко удаляет запись. |
| Суммы нет                              | Форма заполняется (карта, категория, название), курсор в «Стоимость»; ничего не сохраняется, пока человек сам не нажмёт «Добавить».             |
| Строка шаблона с суммой в панели «Все» | Кнопка «В форму»: шаблон кладётся в форму, чтобы подправить перед сохранением.                                                                  |

Сумма видна на чипе до нажатия: это защита от случайного тапа. Нужна ли предварительная подтверждающая стадия, решается после проверки на практике (раздел 8).

### UI: создание и управление

- **Создание:** пункт «Сохранить как шаблон» в меню «⋯» операции (`OperationsTable`; он добавлен в уже существующее меню, строкам без меню меню не появляется) открывает диалог с уже заполненными полями (название кнопки, категория, карта, переключатель «Сохранить сумму», область «Только мне» / «Группе»). Второй путь: кнопка «В шаблон» в тосте успеха после сохранения расхода (4 секунды, показывается, только если у такой траты ещё нет шаблона). Третий: Настройки → «Шаблоны» → «Новый».
- **Управление: Настройки → «Шаблоны».** Раздел «Мои» (меню «⋯»: изменить, выше, ниже, поделиться, удалить; порядок меняется перетаскиванием), раздел «Группа» (переключатель показа у каждого; владелец дополнительно редактирует и убирает), переключатели «Скрыть все групповые» и «Полоска над формой».
- Макеты: артефакт «Шаблоны расходов, варианты UX» (кликабельная схема всех экранов выше).

### API и мобильные сценарии

Шаблоны доступны через `/api/v1` (раздел 3), поэтому кнопка Home Assistant вызывает тот же шаблон: `POST /api/v1/templates/:id/apply`. Правила выбора карты и валюты те же, что в интерфейсе.

## 5. Telegram (этап 3 уведомления, этап 4 мониторинг)

**Бот.** Один на установку. Токен бота и id чата администратора для мониторинга лежат в серверном `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`; единственный источник, чтобы внешний скрипт мониторинга работал и при упавшем приложении; права файла 600, значения не печатаются и не логируются). Вход приложения в Telegram: длинный опрос (`getUpdates`), входящий порт не нужен.

**Привязка.** Настройки → «Уведомления в Telegram»: «Привязать» выдаёт одноразовый код (живёт 10 минут, хранится хешем), пользователь отправляет боту `/start КОД`, чат привязывается к его учётной записи. «Отвязать» и «Отправить тест». Блок виден, только если бот включён администратором.

**События (у каждого пользователя свои переключатели).**

| Событие                                          | Кому                                                        |
| ------------------------------------------------ | ----------------------------------------------------------- |
| Лимит категории или общий: 80% и 100%            | владелец группы и по желанию любой участник по своим картам |
| Дневной лимит ИИ почти исчерпан / ошибки ИИ      | администратор                                               |
| Приложение недоступно, мало места, бэкап устарел | администратор (этап 4)                                      |

- Лимит: **одно сообщение на порог за период** (`notification_log`: ключ события, период), без повторов; пересчёт после правок и удалений не шлёт заново.
- Сообщения короткие, на русском, со ссылкой на нужную страницу.

**Мониторинг (этап 4).** Скрипт `scripts/watchdog.sh` по cron на сервере каждые 5 минут проверяет `/api/ready`, место на диске, возраст последнего бэкапа (БД и чеков) и шлёт сообщение напрямую в Telegram. Одно сообщение при поломке и одно при восстановлении, без спама. Не зависит от приложения.

## 6. Товары из чеков (этап 5)

**Проблема.** «Молоко 3,2%», «MILK Parmalat 1L», «Կաթ» это один товар.

**Решение (пробуем, качество проверяем на реальных чеках).**

- В позиции новое поле `product` (общее название, строчными) и `product_source` (`ai`/`manual`). Исходное название с чека остаётся как есть.
- **Нормализация при разборе чека.** В тот же запрос к модели добавляется поле `product` для каждой позиции. В промпт передаётся список уже существующих товаров группы (самые частые, не больше 200), и модель **переиспользует** их, а новое название придумывает, только если ничего не подходит. Дополнительного вызова модели нет.
- **Ручная правка.** В позиции можно изменить товар. Исправление запоминается как `product_aliases` (название с чека → товар) и применяется к следующим позициям с таким же названием без модели.
- **Управление.** Список товаров группы с числом позиций: переименовать, **слить несколько в один**. Видно только владельцу группы.
- **Аналитика.** Вкладка «Товары»: топ товаров по сумме и количеству, динамика цены за единицу (по `price / quantity`), по периоду и карте с обычными фильтрами. Позиции без товара показываются как «Без товара» (ручные позиции, чеки до этапа).
- Старые чеки можно обработать пакетно одним действием администратора (расходует лимит ИИ, делается по желанию).
- Риск: качество нормализации зависит от реальных чеков, поэтому этап последний и начинается после проверки Gemini.

## 8. Импорт расходов из банковских уведомлений (iOS Shortcuts)

Статус: **реализовано в ветке `v5`** (бэкенд и интерфейс). Автоматизация на iPhone настраивается владельцем один раз: уведомление IDBank о покупке (`GNUM`) уходит на сервер, сервер читает его и создаёт расход.

**Решения (по заданию «разработчик решает сам»).**

- **Адрес.** Текущий домен: `POST https://expenses.smartyalta.ru/api/v1/transactions/import`. Отдельный домен не нужен: Caddy уже отдаёт `/api/*` бэкенду, ключ идёт заголовком по HTTPS. Публичный слой `/api/v1` общий с будущим API для Home Assistant (раздел 3). В техзадании пример `/v1/api/...`; выбран `/api/v1/...` как в остальном API.
- **Ключи.** Постоянные, **привязаны к группе** (`api_keys`), несколько на группу, без срока, отзываются мгновенно (`revoked_at`). В базе только SHA-256, показывается один раз при создании (`etk_` + 32 случайных байта). Ключ годится **только для импорта**: на остальных маршрутах он не работает. Управляет ключами владелец группы (Группа → Интеграции). Импортированный расход помечен в списке операций значком банка (`fromBank`). Расходы создаются от имени автора ключа и в пределах его прав на карты.
- **Авторизация без cookie.** Маршрут помечен `config: { public: true, apiKey: true }`: нет входа в приложение и нет проверки Origin (запрос идёт не из браузера). Ограничение частоты: 60 запросов в минуту на ключ и 20 с одного адреса при неверных ключах. Заголовок `Authorization` не попадает в логи.
- **Парсеры.** `modules/bank-import/parsers`: интерфейс `NotificationParser` и реестр по `source`; новый банк это новый файл парсера. Парсер IDBank читает покупку `GNUM`: сумма покупки (не остаток), валюта, продавец, последние 4 цифры карты, дата и время (UTC+4, у Армении нет перехода на летнее время). Строки узнаются по форме, не по номеру строки. Другие виды уведомлений (`unsupported`) и нечитаемый текст (`parse_error`) расход не создают.
- **Карта.** По последним 4 цифрам (`cards.last4`, поле в настройках карты). Нет совпадения или их несколько: **карта не выбирается наугад**, расход не создаётся (`card_not_found` / `card_ambiguous`), попытка видна в «Последних импортах».
- **Категория.** Берётся из прежних расходов группы: то же название продавца, либо **похожее** (одно название входит в другое по словам: «Urartu» и «URARTU ZAQYAN», общее слово не короче 4 букв; слова вроде LLC и «магазин» не считаются). Точное совпадение важнее частичного, при равных побеждает более свежий расход. Если пользователь поменял категорию у импортированного расхода, в следующий раз берётся его выбор. Иначе «другое», иначе первая категория группы. ИИ не используется. Не покрыто: транслитерация (кириллица и латиница считаются разными словами).
- **Дубликаты.** Отпечаток операции: группа, банк, карта, сумма, валюта, продавец, время до минуты (`bank_imports.fingerprint`, уникален среди созданных). Повтор того же уведомления возвращает `duplicate` без нового расхода; две покупки на ту же сумму в разное время не дубликаты.
- **Создание.** Обычным `ExpenseService.create` в одной транзакции с записью импорта: валюты, курс, зеркало в Excel работают как для ручного расхода. Ошибка создаёт запись об ошибке, но не расход.
- **Журнал.** `bank_imports` хранит каждую попытку (статус, разобранные поля, текст уведомления для диагностики). Текст виден только в базе, в интерфейсе показываются разобранные поля.

**Ответы.** `201 created` (+ `transactionId`), `200 duplicate`, `401 unauthorized`, `400 unknown_source` / `invalid_request`, `422 parse_error` / `unsupported` / `card_not_found` / `card_ambiguous` / `error`, `429 rate_limited`. Тело: `{ "success": bool, "status": "...", ... }`.

**Настройка на iPhone.** Приложение «Команды» → Автоматизация → триггер «Уведомление» (приложение IDBank, заголовок содержит `GNUM`) → «Получить содержимое URL»: POST, заголовки `Authorization: Bearer <ключ>` и `Content-Type: application/json`, тело JSON `{ "source": "idbank", "title": <название уведомления>, "body": <текст уведомления> }`, где `title` и `body` это **переменные Команд**, а не текст. Отключить «Запрашивать перед запуском». В задании в п. 9 сказано «уведомление от Idram»: это опечатка, нужен IDBank. Инструкция есть в интерфейсе (Группа → Интеграции).

**Не входит в первую версию (задел есть).** Возвраты и поступления, другие банки, ручное сопоставление карт кроме 4 цифр, повторная обработка нераспознанных, фильтр истории, очистка старых текстов уведомлений.

### 8.1. Apple Wallet и журнал запросов

**Один endpoint, один контракт.** `POST /api/v1/transactions/import`, поля `source`, `title`, `body` не изменились: запросы IDBank работают как раньше. Для Wallet `source: "apple_wallet"` и любые дополнительные необязательные поля (`transaction`, `merchant`, `amount`, `card`, `name`, `receivedAt`, `currency`, `category`, `cardLast4`, `transactionId`, `device`). Неизвестные поля не ошибка: они сохраняются в журнале. Лимит тела запроса 32 КБ.

**Один ключ или два.** Серверу всё равно: ключи равноправны. Рекомендуется **отдельный ключ на каждую автоматизацию** («iPhone — IDBank», «iPhone — Wallet»): его имя видно в журнале (кто прислал), и один можно отозвать, не трогая другой.

**Журнал запросов** (`import_log`, 30 дней). Для каждого запроса с верным ключом: весь JSON как пришёл (в том числе `device`; всё, что похоже на ключ, вырезается; длинные значения обрезаются), источник, ключ, время, статус, причина, что прочитал сервер (`parsed`), с чем совпал (`match`), id расхода. Пишется и для дубликатов и для нераспознанных. Заголовок `Authorization` и ключи не сохраняются. Смотрит только владелец группы: Группа → Интеграции → «Журнал запросов» (`GET /api/group/import-log`). Раз в сутки старше 30 дней удаляется. В обычный лог сервера пишется только строка «источник, статус, ключ», без сумм и текстов.

**Чтение Wallet** (`parsers/apple-wallet.ts`; формат данных Shortcuts заранее неизвестен, поэтому каждое поле необязательно, а факт ищется в нескольких местах):

- продавец: `merchant`, `name`, `title`, затем слова перед суммой в `body`/`transaction`;
- сумма: `amount`, `transaction`, `body`; число принимается только рядом с валютой («Kiosk 4 — 1950 AMD» даёт 1950, не 4); формы: `1950 AMD`, `AMD 1,950.00`, `1 950,50 ֏`, `$12.50`;
- валюта: `currency`, затем рядом с суммой, затем в других полях; нет суммы или валюты: расход не создаётся;
- карта: `cardLast4` как цифры; `card` только как подсказка (имя карты в Wallet не её номер; цифры Apple Pay могут отличаться от цифр пластика); совпадение с картой приложения по словам названия, только если оно единственное;
- время: `receivedAt` (если читается), иначе момент получения; дата берётся из него (у ISO со сдвигом это дата на месте покупки);
- категория: `category` применяется, только если в группе есть категория с точно таким названием (после истории продавца); новые категории не создаются.

**Ответ.** Как раньше (`created`, `duplicate`); для Wallet, если расход не создан, `200 {success:true, status:"unrecognized", importId, message}` (принято и сохранено, повторять не нужно). Для IDBank коды ошибок прежние.

**Один покупка, два источника.** Если расход из другого источника уже есть, новый запрос не создаёт второй: ответ `duplicate` с id существующего.

- **Совпадение:** тот же счёт суммы и валюты, время в пределах ±20 минут и (похожее название продавца **или** та же карта). Разные покупки на ту же сумму не склеиваются: нужен продавец или карта.
- **Приоритет Wallet:** его название продавца «человеческое» (Urartu Zaqyan, а не URARTU ZAQYAN). Если банк пришёл первым, а потом Wallet, расход **переименовывается** по Wallet, только пока название не менял человек (через обычный редактор, с записью в журнал изменений). Карту и категорию банк определяет надёжнее: они остаются.
- **Wallet первым без карты:** запрос сохраняется как `unrecognized`; когда приходит банковское уведомление о той же покупке, расход создаётся с названием из Wallet, а запрос Wallet получает статус `merged` и ссылку на расход.
- **Wallet первым с картой:** расход создан; банк потом получает `duplicate`.
- Повтор того же запроса: тот же отпечаток операции, `duplicate`.

**Обучение на исправлениях.** При импорте смотрится, во что превратились прежние импорты этого магазина **сейчас** (человек мог изменить название и категорию расхода): точно то же название магазина даёт то же **название и категорию**, похожее («Urartu» внутри «URARTU ZAQYAN BRANCH 2») только **категорию** (это может быть другой филиал). Приоритет категории: исправление человека, затем история расходов с таким названием, затем категория Wallet, затем категория ключа, затем «другое». Сумма в правило не входит.

**Время из Wallet.** Читается ISO (лучше всего, с поясом) и то, как показывает телефон: «17 окт. 2026 г., 15:26», «17.10.2026 15:26» (в поясе человека). Не прочиталось: время получения запроса сервером.

**Запросы, которые нельзя принять** (нет `source`, пустой `body` у IDBank) сохраняются в журнале со статусом `invalid_request`, ответ `400` с понятной причиной и `importId`. Пробный запуск автоматизации кнопкой без настоящего уведомления даёт пустые переменные: это нормально.

**Что выяснить по реальным запросам** (см. журнал): какие поля реально присылает Shortcuts, есть ли цифры карты, формат суммы, категория; после этого уточнить сопоставление карты (например, имя карты в Wallet в настройках карты).

## 9. Уведомления в приложении: колокольчик (этап 1) и Web Push (этап 2)

Статус: **этап 1 реализован в ветке `v5`**, этап 2 (Web Push) впереди. Идея: один сервис уведомлений (`modules/notifications`), его события потом рассылаются и по другим каналам (Web Push, Telegram из раздела 5), а лента в приложении работает везде без разрешений.

**События (этап 1)**

| Событие            | Кому                                                                      | Пример                                                                 |
| ------------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `expense_imported` | Всем, кто видит карту расхода: владельцам и участникам с доступом к карте | «Расход добавлен: 2 150 AMD · Food Court 7 · Visa Digital · из Wallet» |
| `import_problem`   | Владельцам группы (они управляют ключами и журналом)                      | «Не удалось добавить расход: Wallet: не удалось определить карту»      |
| `receipt_parsed`   | Тому, кто запросил разбор чека                                            | «Чек распознан: 1 500 AMD · позиций: 2»                                |

- Одна покупка из двух источников (IDBank и Wallet) даёт **одно** уведомление (ключ дедупликации `expense_imported:<id расхода>` уникален для человека). Повтор запроса и «дубликат» уведомлений не создают.
- Wallet-запрос, который сначала не распознался (нет карты), а потом был объединён банковским уведомлением, «снимает» своё уведомление о проблеме: остаётся только «Расход добавлен».
- «Другой вид уведомления» банка (не покупка) не шумит.
- Лента хранится у каждого человека отдельно: прочитанные 30 дней, непрочитанные 90 (суточное обслуживание).
- Решение владельца: каждому участнику приходят уведомления о расходах по его картам; настройки (что и куда присылать) будут позже, в настройках пользователя.

**API** (вход обязателен, видна только своя лента): `GET /api/notifications?limit&before`, `GET /api/notifications/unread-count` (для значка, опрос раз в минуту), `POST /api/notifications/read` (`{ids?}`).

**Интерфейс:** колокольчик в шапке у каждого пользователя со счётчиком; на телефоне нижняя панель, на компьютере всплывающее окно; тап по записи открывает ссылку. **Прочтение:** запись становится прочитанной сама, когда была на экране в открытой панели не меньше ~0,8 с (на 60% и больше), пачкой одним запросом; «Прочитать все» остаётся. **Скрытие:** смахивание влево (красная область «Скрыть»), крестик и клавиша Delete на компьютере, «Скрыть все»; после скрытия 6 секунд доступна отмена «Вернуть». Скрытая запись не показывается и не считается, но остаётся в таблице (`dismissed_at`), чтобы то же событие не вернулось (повтор запроса банка).

## 9а. Web Push (этап 2)

Статус: **проект и реализация в ветке `v5`**. Уведомления из раздела 9 приходят и на экран блокировки, даже когда приложение закрыто. Без Firebase и нативного приложения: стандартный Web Push (Service Worker + Push API + VAPID), сервер отправляет напрямую службам Apple, Google, Mozilla.

### Что важно знать про платформы

- **iPhone (iOS 16.4+):** только для приложения, **добавленного на экран «Домой»** (Safari → «Поделиться» → «На экран Домой») и открытого оттуда. Из обычной вкладки Safari подписаться нельзя. Разрешение запрашивается **только по нажатию** кнопки (нельзя при открытии). Каждое push-сообщение обязано показать уведомление (`userVisibleOnly`): «тихие» сообщения iOS не терпит и отзывает подписку. Манифест уже `display: standalone`.
- **Android (Chrome и другие):** работает и во вкладке, и в установленном приложении. **Компьютер:** Chrome, Edge, Firefox, Safari 16+.
- Подписка принадлежит **устройству и браузеру**, а не человеку: у человека их несколько. Может внезапно протухнуть (410 Gone) или потеряться при сбросе данных сайта.
- Сообщение шифруется для устройства (aes128gcm, ключи подписки), служба Apple/Google его прочитать не может, видит только факт и размер. Но **текст появится на экране блокировки**: для этого есть настройка приватности.
- Сервер сам шлёт запрос по адресу, который прислал клиент (`endpoint`). Это канал для атаки на сервер (SSRF), поэтому разрешены **только адреса известных служб** (см. «Безопасность»).

### Решения

| Вопрос                      | Решение                                                                                                                                                                                                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Библиотека                  | `web-push` (шифрование и подпись VAPID не пишем сами)                                                                                                                                                                                                                                     |
| Ключи                       | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (mailto:) в серверном `.env`; без них Web Push выключен, раздел в настройках показывает «не настроено на сервере»; ключи создаются один раз и **не меняются** (смена отключит все устройства); `npm run push:keys` печатает пару |
| Service Worker              | один файл `/sw.js` в корне (scope `/`), без кэша и без `fetch`-обработчика (не ломает обновления приложения); `no-cache` уже стоит у Caddy для всего, кроме `/assets`                                                                                                                     |
| Когда спрашивать разрешение | только по кнопке «Включить уведомления на этом устройстве» в Настройки → Уведомления                                                                                                                                                                                                      |
| Что шлём                    | те же события, что в колокольчике (`expense_imported`, `import_problem`, `receipt_parsed`), **та же запись и тот же дедуп**: одна покупка из IDBank и Wallet даёт один push                                                                                                               |
| Тексты                      | как в ленте; в режиме приватности без сумм и магазина: «Расход добавлен · из IDBank»                                                                                                                                                                                                      |
| Настройки (на человека)     | какие события присылать push (по умолчанию: расходы и ошибки импорта да, распознанный чек нет, т. к. человек сам это видит), «не показывать суммы на экране блокировки» (по умолчанию нет). Лента-колокольчик всегда получает всё                                                         |
| Устройства                  | список своих устройств с названием («iPhone · Safari», «Chrome · Windows») и «Отключить» (тестовых уведомлений нет: на практике хватает покупки; подсказка про режим «Не беспокоить» / «Фокус» на iPhone: приложение нужно добавить в исключения)                                         |
| Выход из приложения         | при выходе подписка этого устройства **удаляется** (чтобы чужой человек за общим устройством не получал ваши суммы)                                                                                                                                                                       |
| Значок на иконке            | `navigator.setAppBadge(число непрочитанных)`, там где поддерживается (iOS 16.4+ PWA, Chrome); сбрасывается при прочтении                                                                                                                                                                  |
| Нажатие                     | открывает приложение на нужной странице (уже открытое окно переиспользуется)                                                                                                                                                                                                              |
| Недоставка                  | 404/410: подписка удаляется сразу; 429/5xx: две повторные попытки с паузой; другие ошибки считаются, после 10 подряд подписка удаляется                                                                                                                                                   |

| Лимит                       | не больше 10 push в минуту на человека (остальное только в ленте), не больше 10 устройств на человека                                                                                                                                                                                     |
| Не блокировать              | push уходит в фоне после записи в ленту; ошибка push никогда не ломает импорт                                                                                                                                                                                                             |

### Безопасность и приватность

- **Только известные службы** по адресу подписки: `https://`, порт 443, без логина в адресе, не IP: `fcm.googleapis.com`, `*.push.apple.com`, `updates.push.services.mozilla.com`, `*.push.services.mozilla.com`, `*.notify.windows.com` (+ необязательный `PUSH_ALLOWED_HOSTS` для своих). Остальное отвергается 422.
- Адрес и ключи подписки это секрет доступа к устройству: не логируются, не возвращаются в ответах (в списке устройств только название, даты и статус).
- Своя подписка: человек видит и удаляет только свои устройства; тот же `endpoint` у другого человека перепривязывается к вошедшему (общее устройство).
- Закрытый ключ VAPID только в `.env` сервера (права 600), не в репозитории и не в логах.
- Лимит частоты на создание подписки.

### API

`GET /api/push/config` → `{ enabled, publicKey }`; `GET/POST /api/push/subscriptions`, `DELETE /api/push/subscriptions/:id`, `POST /api/push/subscriptions/unsubscribe` (по адресу этого устройства, для выхода), `GET/PUT /api/notifications/settings` → `{ push: { types: { expense_imported, import_problem, receipt_parsed }, hideAmounts } }`.

### Интерфейс

Настройки → «Уведомления»: состояние устройства словами (не поддерживается / нужно добавить на «Домой» с инструкцией / запрещено, как разрешить / выключено / включено), кнопка включения, список устройств, выбор событий с пояснениями, выбор приватности (сегментированный переключатель с примером того, как будет выглядеть уведомление). Ссылка «Настроить уведомления» внизу панели колокольчика.

### Сообщения от владельца и администратора

Владелец группы пишет **участникам своей группы**, администратор **любым пользователям** (всем, или выбранным из любых групп). Это обычное уведомление типа `announcement` (колокольчик и push, у получателя отдельная настройка «Присылать»): `POST /api/notifications/broadcast`, список адресатов `GET /api/notifications/recipients` (владелец видит только свою группу, остальные получают 403), история отправленных `GET /api/notifications/broadcasts`. Заголовок по умолчанию «Сообщение · <имя>», текст до 300 знаков, не больше 10 сообщений в час от одного человека и 200 получателей за раз. Отправитель не получает своё сообщение; выбор человека вне разрешённого круга отвергается как несуществующий. Интерфейс: карточка «Сообщение участникам» на странице «Группа», «Рассылка» на странице «Админ» (один общий компонент): заголовок, текст со счётчиком, «Кому» (всем / выбрать), «Получат: N человек», предпросмотр, подтверждение, история.

### Мгновенный счётчик (SSE)

Приложение держит открытым `GET /api/notifications/stream` (Server-Sent Events): первым сообщением текущее число непрочитанных, дальше каждое изменение (новое уведомление или прочтение в другой вкладке). Запасной опрос раз в ~30 секунд остаётся. Прокси (Caddy) не должен буферизовать этот адрес: для него стоит `flush_interval -1`, ответ идёт с `Content-Encoding: identity`.

### Что нельзя проверить без реального устройства

Доставка на iPhone/Android проверяется только на настоящем устройстве; в тестах используется поддельный отправитель. Первый тест: включить на устройстве, нажать «Отправить тестовое», сделать покупку.

## 10. Открытые вопросы

- Шаблон с суммой создаёт расход сразу (с отменой на 6 секунд). Достаточно ли «отмены» или нужен предварительный показ? Решить после практики.
- Визуальное оформление чипов и панели (цвета, иконки, эмодзи): владелец доработает сам.
- Нужны ли токены только для чтения для отдельных карт (сейчас токен наследует всё, что видит пользователь)?
- Уведомления о лимитах получает только владелец или каждый участник по своим картам (в проекте: по выбору каждого)?
