## 1. Цели и принципы

**Цели**

- Операция может содержать **позиции** (items): названия продуктов, блюд и т.п. и их цены.
- При загрузке фото чека **название, позиции и цены заполняются автоматически** (Gemini), если пользователь не ввёл их сам.
- Всё сгенерированное ИИ **явно помечено**.

**Принципы**

- **Позиции необязательны** и не засоряют вкладку «Добавить»: по умолчанию их не видно, раскрываются по желанию или появляются после разбора чека.
- **Простота для участника** (как в v2 и v3): всё новое включается администратором и владельцем группы, по умолчанию выключено.
- **Ручной ввод главнее ИИ.** ИИ только предлагает и никогда не затирает то, что человек ввёл сам (раздел 5).
- **Сумма операции остаётся источником правды** для аналитики, лимитов и отчётов. Позиции её не заменяют (раздел 3).
- **Работа с LLM изолирована в отдельном модуле** (раздел 7): остальной код не знает про Gemini.
- **Данные не теряются.** Миграции только вперёд, перед выкладкой бэкап базы; ничего не стираем физически.

## 3. Позиции операции (items)

Позиция: `название`, `цена`, `количество` (необязательно, по умолчанию 1), порядок.

- Цена позиции хранится **в валюте карты операции**, с теми же правилами знаков после запятой, что и сумма (драмы без копеек, остальные два знака).
- **Сумма позиций не обязана совпадать с суммой операции.** В чеке бывают скидки, чаевые, округление, нераспознанные строки. Если не сходится, показываем ненавязчивую подсказку «Позиции: N, сумма X, разница Y»; сохранению это не мешает.
- Позиции не участвуют в аналитике, лимитах и отчёте в v4 (только хранение и показ). Аналитика по позициям отложена (раздел 17).
- Максимум **100 позиций** на операцию, название до 200 символов (защита от мусора от модели).
- Правка и удаление позиций идут по тем же правам, что и правка траты (владелец, участник в своём окне правки). Все изменения пишутся в журнал, как у траты.
- Мягкое удаление не нужно: позиции принадлежат операции и меняются вместе с ней единым списком; прежнее состояние хранится в журнале изменений.

## 4. Разбор чека через Gemini

Исходные данные: фото чека, прикреплённое в v3 (категории, где фото разрешено, остаются как есть).

**Поток**

1. Пользователь прикрепляет фото при добавлении или правке траты (как в v3).
2. Если ИИ включён (раздел 8) и фото есть, запускается **разбор**: сервер отправляет изображение в Gemini и получает структурированный ответ.
3. Ответ проверяется (схема, лимиты, числа), затем применяется по правилу раздела 5.
4. Клиент показывает результат с пометкой AI; пользователь может поправить или отклонить.

**Что просим у модели** (ответ строго JSON по схеме, `responseSchema`):

- `name`: короткое название операции (магазин или заведение, при желании основная покупка);
- `items[]`: `name`, `price`, `quantity`;
- `total`: итог чека, чтобы сверить с суммой операции (только для подсказки, в операцию не подставляется);
- `currency`: если видна на чеке (только для сверки, см. вопрос 1);
- `confidence` не требуем, модели его завышают.

**Синхронно или фоном.** Разбор занимает секунды. Допущение: **запрос разбора отдельный** (`POST /api/expenses/:id/receipt/parse`), трата сохраняется и без него, форма не ждёт ответа. При добавлении без сети (v3 §11) очередь сначала отправляет трату и фото, затем клиент запрашивает разбор. Так сбой Gemini никогда не блокирует сохранение траты.

**Повторный разбор.** Кнопка «Разобрать чек заново» (для владельца/автора) доступна, пока включён ИИ; применяется то же правило «только пустое» (раздел 5), если пользователь явно не выбрал «Заменить сгенерированное».

## 5. Правило «не перезаписывать ручной ввод»

«Не заполнено вручную» нужно определять надёжно, поэтому у каждого поля, которое может заполнить ИИ, хранится **источник**:

| Источник | Значение |
|---|---|
| `manual` | ввёл человек (или человек отредактировал текст, предложенный ИИ) |
| `ai` | заполнено ИИ и не менялось человеком |

Правила применения результата разбора:

- **Название операции.** Пустое или источник `ai` → записываем из ответа. Источник `manual` → не трогаем. Название по умолчанию, которое подставляет форма, `manual` не считается.
- **Позиции.** Нет позиций или весь список с источником `ai` → заменяем список. Есть хотя бы одна позиция `manual` → список **не трогаем** (позиции из чека предлагаются отдельной подсказкой «Заменить позиции из чека», без автозаписи).
- **Любая правка человеком** поля с источником `ai` переводит его в `manual` и снимает пометку AI. Это единственное место, где ИИ-данные становятся «ручными».
- Отклонение: «Убрать сгенерированное» удаляет значения с источником `ai`, остальное остаётся.

Сумма, дата, карта и категория ИИ не меняются никогда.

## 6. Пометка «сгенерировано с помощью AI»

- Рядом с названием операции и над списком позиций, если источник `ai`: небольшой значок (звёздочка/искра) с подписью **«Сгенерировано с помощью AI»**; на узком экране значок с подсказкой (`title` и `aria-label`).
- Пометка видна **всем, кто видит операцию** (в списке операций, в карточке, в отчёте Excel не добавляем).
- В выгрузках и API поле источника отдаётся, чтобы внешние потребители могли отличить данные.
- Пометка исчезает при ручной правке соответствующего поля (раздел 5). Если часть позиций исправлена вручную, весь список становится `manual`, пометки у неизменённых позиций не остаются (допущение: простота важнее точности; если нужна пометка по каждой позиции, решаем отдельно, вопрос 5).

## 7. Модуль LLM в коде

Отдельный модуль, **один вход и одна ответственность**. Остальной код видит только интерфейс.

```
backend/src/modules/llm/
  llm.types.ts            # интерфейс провайдера, ReceiptParseResult, ошибки
  llm.service.ts          # включён ли ИИ, проверка лимитов, вызов провайдера, проверка ответа
  llm.settings.ts         # чтение/запись настроек (флаг, ключ, модель) в app_settings
  llm.routes.ts           # админские маршруты настроек и проверки ключа
  receipt-parser.ts       # промт и JSON-схема для чека, преобразование ответа
  providers/
    gemini.provider.ts    # единственное место, которое знает про Gemini API (fetch, без тяжёлого SDK)
    fake.provider.ts      # детерминированный провайдер для тестов
```

- **Интерфейс провайдера**: `parseReceipt(image, options) → ReceiptParseResult`. Gemini реализует его; смена провайдера = новый файл в `providers/`.
- **Модуль receipts/expenses** вызывает только `llm.service`, не зная ключей и форматов Gemini.
- **Зависимость внедряется** в `buildApp` (как `receipts` и `budgets`), в тестах подставляется `fake.provider`.
- Работа с сетью без SDK (`fetch` из Node 20+), таймаут, один повтор при 429/5xx с паузой. Новых тяжёлых зависимостей не добавляем.
- Все настройки (`GEMINI_MODEL` по умолчанию и т.п.) идут через `src/config/env.ts` и документируются в README и `.env.example`, как требует `backend/CLAUDE.md`.
- Расширяемость: в `llm.service` есть понятие «задача» (`receipt-parse`), под которое позже можно добавить другие (автокатегория, v3 §5), не меняя провайдеров.

## 8. Включение и настройки

Два независимых выключателя; ИИ работает, только если **включены оба** и ключ задан.

| Уровень | Где | Кто | По умолчанию |
|---|---|---|---|
| Установка | Страница «Админ», блок «ИИ (Gemini)» | Администратор приложения | **Выключено** |
| Группа | «Группа» → «Настройки группы» | Владелец группы | **Выключено** |

- Если админ выключил ИИ, переключатель группы виден, но неактивен («Выключено администратором»).
- Выключение **не удаляет** сохранённые позиции и пометки: они остаются, просто нельзя запускать новый разбор.
- Для участника без включённого ИИ интерфейс **не меняется**: никаких кнопок разбора. Позиции (если уже есть) показываются.
- Допущение: ИИ в группе работает для всех категорий, где разрешено фото чека (v3 §9). Отдельный выбор категорий не нужен (вопрос 4).

## 9. API-ключ

- Редактируется **только на странице «Админ»**: поле ввода (скрыто), кнопки «Сохранить», «Проверить», «Удалить ключ».
- **Из API ключ никогда не возвращается**: клиент получает только `задан / не задан` и последние 4 символа. В логах не пишется, в ошибках не показывается.
- Хранение: в `app_settings` в зашифрованном виде (AES-256-GCM), мастер-ключ в переменной окружения `SECRETS_KEY` (в `.env` на сервере, не в базе и не в репозитории). Без `SECRETS_KEY` сохранить ключ из интерфейса нельзя (понятная ошибка), остаётся запасной вариант `GEMINI_API_KEY` из окружения.
- Приоритет: ключ из интерфейса, иначе `GEMINI_API_KEY` из окружения.
- «Проверить» делает минимальный запрос к Gemini и показывает «Ключ работает» или человекопонятную ошибку (неверный ключ, лимит, нет сети), не раскрывая ключ.
- Изменение ключа, включение и выключение пишутся в журнал (кто и когда, без значения ключа).
- Админ также видит модель (редактируемое поле со значением по умолчанию) и счётчик использования (раздел 13).

## 10. Данные и миграции

Новая миграция `0019_items_and_ai.sql` (вперёд, без изменения применённых):

```sql
-- настройки группы
ALTER TABLE groups ADD COLUMN ai_enabled boolean NOT NULL DEFAULT false;

-- источник названия операции: 'manual' | 'ai'
ALTER TABLE expenses ADD COLUMN name_source text NOT NULL DEFAULT 'manual'
  CHECK (name_source IN ('manual', 'ai'));

-- позиции операции
CREATE TABLE expense_items (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  expense_id  uuid        NOT NULL REFERENCES expenses (id),
  group_id    uuid        NOT NULL REFERENCES groups (id),
  position    integer     NOT NULL,
  name        text        NOT NULL CHECK (char_length(name) BETWEEN 1 AND 200),
  price       numeric(14,2) NOT NULL CHECK (price >= 0),
  quantity    numeric(10,3) NOT NULL DEFAULT 1 CHECK (quantity > 0),
  source      text        NOT NULL DEFAULT 'manual' CHECK (source IN ('manual', 'ai')),
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX expense_items_expense_idx ON expense_items (expense_id, position);

-- учёт разборов: для лимитов и статистики
CREATE TABLE ai_usage (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  group_id    uuid        NOT NULL REFERENCES groups (id),
  expense_id  uuid        REFERENCES expenses (id),
  task        text        NOT NULL,
  model       text        NOT NULL,
  status      text        NOT NULL CHECK (status IN ('ok', 'error')),
  error_code  text,
  created_by  text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

- Настройки установки (включено, зашифрованный ключ, модель, лимиты) лежат в существующей `app_settings` (ключи `llm.enabled`, `llm.api_key`, `llm.model`, `llm.daily_limit`).
- Excel-синхронизация (v2, заморожена) **ничего не знает** про позиции: название, пришедшее из ИИ, попадает в Excel как обычное название.
- Изменение позиций пишется в журнал изменений траты (`recordChange`) вместе с остальными полями; снимок строки Excel (`excel_snapshot`) не затрагивается.

## 11. API

| Маршрут | Назначение | Права |
|---|---|---|
| `GET /api/expenses/:id/items` | Позиции операции (также входят в карточку траты) | как чтение траты |
| `PUT /api/expenses/:id/items` | Заменить список позиций целиком | как правка траты |
| `POST /api/expenses/:id/receipt/parse` | Разобрать прикреплённое фото, применить правило раздела 5; ответ: что записано и что пропущено | как правка траты, ИИ включён |
| `DELETE /api/expenses/:id/ai` | «Убрать сгенерированное» | как правка траты |
| `GET /api/ai/status` | Включён ли ИИ для моей группы (для показа кнопок) | любой |
| `GET/PUT /api/admin/ai` | Включение, модель, ключ (запись), статус и использование | администратор |
| `POST /api/admin/ai/test` | Проверить ключ | администратор |
| `PUT /api/group/ai` | Включить ИИ для группы | владелец |

- Создание и правка траты принимают необязательный `items` (список) и `nameSource`; идемпотентность записи и очередь без сети (v3 §11) продолжают работать.
- Все маршруты ограничены `ExpenseScope` и группой пользователя; чужая операция выглядит как несуществующая (404).
- Ошибки: `AppError` с кодом и русским сообщением (`AI_DISABLED`, `AI_KEY_MISSING`, `AI_UNAVAILABLE`, `AI_BAD_RESPONSE`, `AI_LIMIT_REACHED`, `RECEIPT_MISSING`).

## 12. Интерфейс

**Вкладка «Добавить»**

- Позиции **не показываются по умолчанию**. Под формой компактная ссылка «+ Позиции чека» (раскрывает редактор: строки «название, цена», кнопки-иконки добавить и удалить).
- Если прикреплено фото и ИИ включён: после сохранения траты запускается разбор, в форме видно спокойное «Разбираю чек…», затем «Название и позиции заполнены ИИ». Ничего не блокирует следующий ввод.
- Для участников без ИИ форма выглядит так же, как сейчас.

**Список операций и карточка траты**

- В строке: если позиции есть, небольшой счётчик «3 позиции» (необязательно, по клику раскрывает список).
- В карточке (диалоге правки): раздел «Позиции» со списком, редактором, подсказкой о расхождении с суммой и пометкой AI (раздел 6), кнопки «Разобрать чек» (если можно), «Убрать сгенерированное».
- Кнопки в строках, как везде, иконки с `aria-label` и `title`.

**Страница «Админ»**: блок «ИИ (Gemini)»: переключатель, поле ключа (скрыто) с «Сохранить», «Проверить», «Удалить», модель, использование за сегодня и за месяц.

**«Группа» → «Настройки группы»** (владелец): переключатель «Разбор чеков с помощью ИИ» с пояснением, куда уходят фото (раздел 13).

## 13. Безопасность, приватность, стоимость

- **Фото уходит в Google.** Это внешний сервис; владелец группы включает его осознанно. Рядом с переключателем группы показывается короткое пояснение; согласие фиксируется самим включением (допущение, вопрос 6).
- Фото отправляется **без** имени пользователя, группы и других данных, только изображение и инструкция.
- Ключ и мастер-ключ не попадают в логи, ответы, журнал изменений, бэкапы базы в открытом виде (ключ зашифрован).
- Ответ модели **недоверенные данные**: проверяем схему, длины, числа и количество позиций; названия показываем как текст (без HTML); инструкции внутри чека не исполняются, модель не получает инструментов и доступа к данным.
- **Лимиты расхода:** разборов в сутки на группу (по умолчанию 30) и на установку, настраивается админом (`llm.daily_limit`); при превышении `AI_LIMIT_REACHED` с понятным текстом. Один разбор на фото без автоповторов по кругу.
- Размер изображения: клиент уже сжимает фото (v3, 2400 px); для Gemini при необходимости уменьшаем ещё до разумного размера на сервере.
- Использование пишется в `ai_usage`, видно админу (число запросов, ошибок).

## 14. Ошибки и деградация

- Gemini недоступен, ключ неверный, лимит исчерпан, ответ не по схеме: трата **уже сохранена**, пользователь видит спокойное «Не удалось разобрать чек, заполните вручную» и может повторить позже.
- Нет сети: разбор не запускается, остаётся кнопка «Разобрать чек» после появления связи.
- Частично корректный ответ: применяем валидные позиции, битые отбрасываем и сообщаем «Распознано N из M».
- Выключили ИИ посреди работы: новые разборы отклоняются `AI_DISABLED`, уже записанное не трогаем.
- Без `SECRETS_KEY` и без `GEMINI_API_KEY` приложение запускается как обычно, ИИ просто недоступен.

## 15. Тесты

- Backend (Vitest на PGlite, `fake.provider`): правило раздела 5 (каждая комбинация источников), права и скоуп группы, два выключателя и ключ, лимиты, шифрование ключа (ключ не возвращается ни одним маршрутом), валидация ответа (мусор, лишние позиции, отрицательные цены), журнал изменений, идемпотентность.
- Контрактные тесты `gemini.provider` на записанных ответах (без обращения к сети в CI); живой тест с реальным ключом пропускается по умолчанию, как живые тесты OneDrive.
- Frontend: редактор позиций (необязателен, скрыт по умолчанию), пометка AI появляется и исчезает при ручной правке, ссылки и кнопки скрыты без ИИ, поведение при ошибке разбора.
- Ручная проверка: несколько реальных чеков (магазин, кафе, на армянском/русском/английском), оценка точности перед включением для всех.

## 16. Порядок работ

1. Модуль `llm` с интерфейсом, `fake.provider`, настройками и шифрованием ключа; страница «Админ» (ключ, переключатель, проверка).
2. Миграция `0019`, позиции операции (хранение, API, журнал, редактор в интерфейсе, без ИИ).
3. Провайдер Gemini и разбор чека, правило раздела 5, пометка AI, переключатель группы, лимиты.
4. Подбор промта и модели на реальных чеках, документация (`PIPELINE.md`, README бэкенда, `.env.example`).

Каждый этап выкладывается отдельно, с бэкапом базы перед миграциями.

## 17. Не входит в v4

- Аналитика и лимиты по позициям (категории позиций, «сколько на молочку»): возможный v5.
- Автоматические категории и суммы из чека, разбиение одной траты по категориям.
- Распознавание текста без ИИ (локальный OCR), другие провайдеры (интерфейс готов, реализации нет).
- Чтение чеков по QR-коду и фискальным API.
- Позиции в отчёте Excel и в синхронизации с Excel (заморожена).

## 18. Открытые вопросы

Ответы нужны до реализации; в скобках мой вариант по умолчанию.

1. **Сумма и валюта из чека.** Только подсказка при расхождении (да), или подставлять сумму, если поле пустое? Сейчас сумма вводится первой, и при добавлении без неё трату не сохранить.
2. **Когда запускать разбор:** автоматически после сохранения траты с фото (рекомендую) или только по кнопке?
3. **Позиции без ИИ:** нужны ли они вручную всем (раскрываемый редактор) или только там, где включён ИИ?
4. **Включение по категориям:** хватит группового переключателя (разбор там, где разрешено фото) или нужен отдельный выбор категорий?
5. **Пометка AI:** одна на весь список позиций (проще) или на каждую позицию?
6. **Согласие на отправку фото в Google:** достаточно факта включения владельцем или показывать участнику уведомление при первой загрузке фото?
7. **Мастер-ключ `SECRETS_KEY`:** согласны хранить ключ Gemini в базе зашифрованным (так его можно менять на странице «Админ») и добавить `SECRETS_KEY` в `.env` на сервере? Правку сервера применю только по вашему «да».
8. **Лимиты:** подходит ли 30 разборов в сутки на группу по умолчанию?
9. **Модель Gemini:** какую по умолчанию (быстрая Flash-модель дешевле; точную выберем после проверки на реальных чеках)?
