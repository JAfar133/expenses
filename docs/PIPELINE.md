# Как работает приложение: краткий пайплайн

Подробности по частям: [backend/README.md](../backend/README.md), [frontend/README.md](../frontend/README.md),
развёртывание и обслуживание: [DEPLOY.md](DEPLOY.md).

## Схема

```
Браузер (PWA)  ──HTTPS──▶  Caddy (web)  ──/api──▶  backend (Fastify)  ──▶  PostgreSQL (основное хранилище)
                           раздаёт интерфейс                          │
                                                                      └──▶ rclone ──▶ Excel в OneDrive (зеркало)
```

Excel в схеме **необязателен**: без `ONEDRIVE_FILE_PATH` приложение работает только с базой (шаги про Excel ниже пропускаются,
значок синхронизации скрыт). Записи, добавленные в таком режиме, допишутся в Excel сами, если его подключить позже.

Caddy выдаёт сертификат Let's Encrypt, раздаёт собранный интерфейс и проксирует `/api` на backend.
pgAdmin открывается отдельным адресом под паролем Caddy.

## 1. Вход

1. Пользователь открывает сайт и видит форму входа (`misha` или `nastya`).
2. `POST /api/auth/login`: backend сверяет пароль с хешем (scrypt) и ставит две HttpOnly-куки:
   access-токен на 24 часа и refresh-токен на 7 дней.
3. Когда access-токен истекает, интерфейс сам вызывает `POST /api/auth/refresh`. Refresh-токен при этом заменяется
   новым, сессия не длится дольше 30 дней с ввода пароля.
4. Пользователи и пароли берутся из `.env` и записываются в базу при старте backend (в базе только хеши).
5. Защита: 5 неверных паролей за 15 минут блокируют вход, запросы на изменение принимаются только с адреса сайта.

## 2. Добавление расхода

1. В форме по умолчанию выбрана карта вошедшего пользователя. Отправка: `POST /api/expenses` с ключом идемпотентности.
2. Backend в **одной транзакции** сохраняет расход в PostgreSQL вместе с ключом идемпотентности:
   повторная отправка (например, при плохой связи) не создаёт дубль.
   Расход можно ввести в AMD, RUB, USD или EUR. Иностранная сумма (с копейками) пересчитывается в драммы по курсу ЦБ Армении
   (курс подставляется в форму и его можно изменить вручную). В базе хранятся и драммы, и исходная сумма с курсом на момент ввода,
   а в Excel попадает только сумма в драммах. Курсы обновляются раз в несколько часов и сохраняются; если источник недоступен,
   используется последний известный курс.
3. Сразу после этого он пробует дописать строку в Excel (ждёт до `SYNC_INLINE_WAIT_SECONDS`, по умолчанию 15 с):
   - перед записью делается резервная копия файла;
   - файл скачивается, строка добавляется точечной правкой XML и файл загружается обратно через rclone.
4. Результат записи в Excel виден в статусе расхода:
   - `synced`: строка есть и в базе, и в Excel;
   - `pending`: файл занят (например, открыт в Excel на другом устройстве), расход ждёт в очереди и
     дописывается автоматически, как только файл освободится (повторные попытки каждые `SYNC_RETRY_SECONDS`).

Расход не теряется ни при недоступном Excel, ни при сбое сети: источником правды всегда остаётся база.

### Фото чека, позиции и ИИ (v3, v4)

К расходу можно приложить фото чека (файлы в `RECEIPTS_DIR`, ничего не стирается) и список позиций (название, цена всей строки, количество).
Если администратор включил ИИ, добавил ключ Gemini, а владелец включил его для группы и категории, фото разбирается сразу после выбора:
модель возвращает название, дату, категорию, валюту, итог и позиции, форма заполняет только то, что человек не вводил сам, а такие значения помечаются значком ИИ.
Сервер сам проверяет метки (по номеру разбора `aiParseId`), число разборов в сутки ограничено, ключ хранится зашифрованным и наружу не отдаётся.
Повторный разбор того же фото тем же пользователем отдаёт сохранённый ответ без нового вызова модели. Несохранённая форма с фото хранится на устройстве как черновик.
Подробности: [V4_SPEC.md](V4_SPEC.md).

## 3. Синхронизация Excel и базы

Запускается каждые `SYNC_INTERVAL_MINUTES` (5 минут) и по кнопке «Синхронизировать» (значок в шапке показывает состояние).

1. Дописываются расходы из очереди (`pending`).
2. Новые строки, добавленные в Excel вручную, попадают в базу. Одинаковые строки сопоставляются по количеству и не склеиваются.
3. Строки, которых больше нет в Excel или которые там изменены, помечаются в базе **удалёнными** (мягкое удаление, запись не стирается).
   Вернувшиеся в Excel строки восстанавливаются.
4. Защита от массовой потери: если за цикл пропало больше `SYNC_MAX_DELETE_PERCENT` (25%) записей, удаление не применяется,
   значок предупреждает, а применить его можно подтверждением (`POST /api/sync` с `{"applyDeletions": true}`).

## 3.1. Анализ расходов

Раздел «Анализ» (адрес `/analytics`) открывается отдельным фрагментом сборки. Все подсчёты (суммы, расход в день, группировки,
графики по дням) выполняет SQL на сервере (`/api/analytics/*`), в браузер приходят только готовые числа. На главной странице под формой
показано, сколько потрачено в текущем месяце. Все фильтры (период, карты, категории, автор, валюта, поиск, сумма) хранятся в адресной строке и применяются на всех вкладках; вкладка «Сравнение месяцев» сопоставляет месяцы между собой. План развития: [ANALYTICS_PLAN.md](ANALYTICS_PLAN.md).

Над страницей «Анализ» есть выбор валюты показа (с флагами: 🇦🇲 AMD, 🇷🇺 RUB, 🇺🇸 USD, 🇪🇺 EUR). В базе суммы хранятся в драммах, при показе они делятся на текущий курс ЦБ Армении
(курс виден под выбором); проценты, доли и количества от валюты не зависят. Выбор запоминается в настройках пользователя. Журнал «Операции» остаётся в драммах.

## 3.2. Правка и удаление

Вкладка «Операции» показывает все записи с сортировкой, страницами и состоянием каждой относительно Excel (совпадает, ждёт записи, обновления или удаления).
Редакторы (`EDITOR_USERS`, по умолчанию `misha`) могут исправлять и удалять записи; удаление мягкое, запись можно вернуть.
Изменение сначала записывается в базу и в журнал, затем синхронизация заменяет или убирает нужную строку в Excel (тем же способом и с теми же проверками, что и добавление).
Если файл занят, изменение ждёт в очереди. Подробности: [backend/README.md](../backend/README.md#правка-и-удаление-записей).

## 3.3. Настройки пользователя

Страница «Настройки» (`/settings`): аккаунт (имя, карта по умолчанию, часовой пояс; логин не меняется), смена пароля, настройки анализа (виды графиков, панель фильтров), тема оформления (системная, светлая, тёмная) и, для редакторов, права пользователей. Настройки хранятся на сервере
для каждого пользователя, поэтому действуют на всех его устройствах; браузер хранит копию как быстрый кэш. Страница собрана из независимых блоков,
новая настройка это новый блок. Описание всех настроек в одном месте: `frontend/src/features/preferences/model/preferences.ts` (и список разрешённых ключей на сервере).
Пароль, заданный в приложении, остаётся при перезапусках, пока значение в `.env` не менялось.

## 4. Обслуживание

- Раз в сутки удаляются устаревшие резервные копии Excel, ключи идемпотентности и закрытые сессии (`BACKUP_RETENTION_DAYS`).
- Резервные копии базы и восстановление Excel: [DEPLOY.md](DEPLOY.md) (разделы про бэкапы) и `scripts/restore-backup.sh`.

## 5. Выкладка нового кода

```
Mac: git push  ──▶  сервер: ./scripts/deploy.sh
```

Скрипт делает `git pull`, проверяет настройки compose и Caddyfile, пересобирает и перезапускает контейнеры,
ждёт ответа backend. Миграции базы применяются автоматически при старте backend; данные в томах сохраняются.
