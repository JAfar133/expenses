## 1. Цели и принципы

**Цели**

- Дать контроль над тратами (лимиты, «сколько осталось от зарплаты») и сделать ввод быстрее.
- Закрыть эксплуатационные пробелы: видимость бэкапа, лимиты ресурсов сервера.

**Принципы** (как в v2)

- **Простота для участника.** Интерфейс обычного пользователя не усложняется: новое включается владельцем и появляется
  только там, где нужно. Всё необязательное выключено по умолчанию.
- **Опасные операции под контролем.** Всё, что меняет данные массово или настройки сервера, сначала показывает предпросмотр,
  требует явного подтверждения и делает бэкап. Правки сервера (Docker и т.п.) применяются только после одобрения владельца.
- **Данные не теряются.** Миграции только вперёд, перед выкладкой бэкап базы.

## 3. Видимость бэкапа

Сейчас, если ночной бэкап (`scripts/backup-db.sh`, cron в 03:00) упадёт, это не видно до тех пор, пока копия не понадобится.

- Скрипт после каждого запуска пишет файл состояния `backup-status.json` (время, успех или ошибка, имя и размер файла, копия в OneDrive
  загружена или нет) в папку бэкапов. Папка монтируется в backend **только для чтения**.
- Страница «Админ»: блок «Бэкап базы»: время последней копии, размер, статус. Красная плашка, если успешной копии нет больше суток
  или последний запуск закончился ошибкой.
- Уведомление вне приложения (Telegram или почта): по умолчанию не делаем, только плашка. См. открытые вопросы.

## 4. Лимиты и логи Docker

Замер на сервере (2 ГБ ОЗУ, 2 vCPU, рядом работает VPN): backend 83 МБ, postgres 49 МБ, web 42 МБ, pgAdmin 239 МБ, VPN 168 МБ.

Предложение (применяется только после одобрения владельца, сначала показывается дифф `docker-compose.yml`):

- Лимит памяти: backend 256 МБ, postgres 256 МБ, web 96 МБ.
- Ротация логов контейнеров: 10 МБ × 3 файла.
- pgAdmin останавливать, когда он не нужен (экономия около 240 МБ); запуск по требованию (`docker compose up -d pgadmin`).
- Замеры до и после; изменение не должно влиять на VPN.

## 5. Автокатегория по названию

При вводе названия (например, «Такси») категория подставляется по истории группы, если у этого названия есть явно преобладающая категория
(не менее двух записей и доля не ниже 60%). Подставляется только пока пользователь сам не выбрал категорию; выбор всегда можно изменить.
Подсказки названий (`name-suggestions`) уже содержат категории, поэтому нужна в основном правка интерфейса формы.

## 6. Участник правит свою трату

Сейчас править и удалять может только владелец. Участник может исправить или удалить **свою** трату в течение окна, которое задаёт владелец.

- Настройка группы: «Участники могут исправлять свои траты»: выключено / 15 минут / 1 час / 24 часа (по умолчанию 24 часа).
- Только свои траты (по полю «кто добавил»), только по картам с доступом `edit`.
- Правка и удаление попадают в журнал изменений (`expense_changes`) как у владельца.
- Для интерфейса участника: рядом со своей свежей тратой появляется «Изменить» и «Удалить», больше ничего не меняется.

## 7. Бюджеты: лимиты на месяц

- Владелец задаёт **лимит на календарный месяц** на категорию и (необязательно) общий лимит группы. Лимит в валюте отчётности.
- Таблица `budgets`: `group_id`, `category_id` (пусто = общий), `limit_amount`, `created_at`.
- На главной странице и в анализе: «Категория: потрачено X из Y» с полоской; цвет и текст меняются при 80% и 100%.
- Уведомлений вне приложения нет (только индикация в интерфейсе).
- Бюджет видят все участники в пределах доступных им карт (расчёт по тем же правам, что и аналитика).
- Период «от зарплаты до зарплаты» для лимитов не делаем (он нужен только для доходов, раздел 8).

## 8. Доходы

Поступление (например, зарплата) хранится отдельно от трат.

**Данные**

- `incomes`: группа, дата, сумма, валюта, название («Зарплата»), кто внёс.
- `income_allocations` (необязательно): разложение поступления по картам (например, 300 000 на idbank и 200 000 на другую карту).

**Как это показывается**

- **Период «от зарплаты до зарплаты».** Поступление открывает период, который длится до дня перед следующим поступлением с тем же названием
  (если следующего ещё нет, до сегодняшнего дня).
- Главная страница владельца: «Из 500 000 потрачено 312 000, осталось 188 000» и полоска.
- Если поступление разложено по картам: по каждой карте «выделено / потрачено / осталось» за период.
- Валюты: сумма поступления хранится в своей валюте, сравнение идёт в валюте отчётности по курсу дня поступления.

**Права:** доходы видит и меняет **только владелец**. Участникам доходы не показываются.

**Что не делаем:** переводы между картами как отдельную сущность, проценты и инвестиции, учёт баланса счетов.

## 9. Фото чека

Необязательная функция, **выключена по умолчанию**.

- Настройки группы (владелец): включить фото чеков и выбрать **категории**, где можно прикрепить фото (например, «одежда», «здоровье»).
- Фото прикрепляется при добавлении траты и позже при правке, только для выбранных категорий. Прикрепление не обязательное.
- Клиент сжимает снимок до разумного размера (ориентир около 300 КБ, большая сторона до ~1600 px, JPEG).
- Хранение: файлы в томе сервера (`/data/receipts/<группа>/<трата>.jpg`), таблица `expense_attachments` (трата, имя файла, размер, кто добавил).
- Доступ только через авторизованный запрос и по тем же правам, что и к самой трате (скрытая карта: фото не видно).
- **Бэкап файлов:** копия тома с чеками раз в сутки в OneDrive (бэкап базы файлы не содержит).
- Удаление траты не стирает файл сразу (мягкое удаление, как у траты); физическая чистка отдельной задачей.

## 10. Перевод карты в другую валюту

Сейчас валюту карты нельзя менять, если по ней есть траты. Добавляется отдельная **осторожная операция владельца**.

1. Владелец выбирает карту и новую валюту.
2. **Предпросмотр** (ничего не меняется): число затронутых трат, итоговые суммы до и после, курсы (по дню каждой траты из истории курсов,
   при отсутствии ближайший известный).
3. **Подтверждение:** ввод названия карты.
4. Перед запуском **автоматический бэкап базы**.
5. Одна транзакция: пересчёт `card_amount` и `card_currency` у трат карты, запись в журнал изменений (было, стало), смена валюты карты.
6. Отменить нельзя, кроме восстановления из бэкапа; поэтому предпросмотр и подтверждение обязательны.

Риск: суммы по курсам прошлых дней приблизительны для трат до начала истории курсов (v2); предпросмотр это показывает.

## 11. Добавление без сети

Возможно, но с оговорками; решение откладывается.

- Нужен service worker (приложение должно открываться без сети) и очередь в IndexedDB; отправка использует ключ идемпотентности (уже есть).
- На iPhone нет фоновой отправки в Safari: очередь уйдёт, когда приложение откроют снова.
- Курс пересчитывается на сервере в момент отправки (либо запоминается курс из кэша на момент ввода).
- Объём: отдельный небольшой этап.

## 13. Отложено

- CI на GitHub (типы, тесты, сборка на каждый push) и сквозной тест на headless Chrome.
- Политика паролей, смена пароля при первом входе, список входов.
- Удаление кода синхронизации с Excel, разбиение крупного фрагмента графиков, удаление запасных колонок.
- Повторяющиеся траты: не делаем.
