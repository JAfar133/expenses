# Backend

Node.js + TypeScript + Fastify + PostgreSQL. Расходы хранятся в PostgreSQL, а существующая таблица
`Операции` в Excel на OneDrive поддерживается как зеркало: приложение пишет в оба места, а раз в
несколько минут сверяет Excel с базой и подтягивает строки, добавленные в Excel вручную.

## Требования

- Node.js 22+
- PostgreSQL 16+ (локально поднимается через `docker compose`, см. корневой README)
- [rclone](https://rclone.org/) с настроенным remote для личного OneDrive

## Настройка rclone

```bash
rclone config                 # создайте remote типа onedrive (personal), имя: onedrive
rclone lsl "onedrive:Документы/Расходы-dev.xlsx"   # проверка доступа к файлу
```

Файл конфигурации rclone содержит OAuth-токены: не добавляйте его в Git.

## Запуск

Проще всего из корня репозитория: `./scripts/start-all.sh` (он сам поднимет PostgreSQL в Docker).
Только backend:

```bash
npm install
cp .env.example .env
docker compose -f ../docker-compose.yml up -d --wait postgres   # PostgreSQL на 127.0.0.1:5433
npm run dev        # с перезапуском при изменениях
```

При старте backend ждёт базу, применяет миграции, запускает синхронизацию с Excel и слушает
`HOST:PORT` (по умолчанию `127.0.0.1:3000`). Production-сборка: `npm run build && npm run start:prod`.

## Как работает хранение

```
 форма ──POST──▶  PostgreSQL  ──очередь──▶  Excel (OneDrive)
                      ▲                          │
                      └────── синхронизация ◀────┘   (строки, добавленные в Excel вручную)
```

1. **Расход сохраняется в PostgreSQL** (вместе с ключом идемпотентности, в одной транзакции) со
   статусом `pending`. С этого момента он не потеряется.
2. **Сразу пробуем записать его в Excel.** Если получилось — статус `synced`, ответ `excelStatus: "synced"`.
3. **Если Excel недоступен** (файл открыт в Excel на другом устройстве, нет сети, OneDrive не отвечает),
   расход остаётся в очереди, а ответ приходит сразу: `201` с `excelStatus: "queued"`. Очередь
   дописывается в Excel автоматически, как только файл освободится (повтор раз в `SYNC_RETRY_SECONDS`).
4. **Раз в `SYNC_INTERVAL_MINUTES` и по кнопке в интерфейсе** выполняется синхронизация (ниже).

Статусы записи в Excel (`expenses.excel_status`): `pending` — ждёт в очереди, `writing` — запись
начата и результат ещё не подтверждён, `synced` — строка есть в Excel.

Чтение Excel не блокируется открытым файлом, поэтому строки, добавленные вручную, подтягиваются в базу
даже тогда, когда запись в Excel отложена.

## Синхронизация PostgreSQL ↔ Excel

За один цикл (`src/modules/sync/`):

1. Скачивается свежий Excel.
2. **Импорт.** Строки таблицы сверяются с базой. Новые строки (добавлены в Excel вручную) попадают в базу
   с источником `excel`.
3. **Запись очереди.** Записи `pending` дописываются в Excel одним проходом: резервная копия → правка →
   проверка → загрузка.

Как определяются «новые» строки: у строк Excel нет идентификаторов, поэтому одинаковые операции
сопоставляются **по количеству**. Два одинаковых расхода (например, два кофе за день) остаются двумя
записями и не склеиваются. Если в Excel строк больше, чем в базе, лишние импортируются.

Расхождения: если строку **удалили или изменили** в Excel, запись в базе не удаляется и не меняется.
Приложение считает такие записи (`diverged`) и показывает счётчик в интерфейсе. Изменённая строка при
этом импортируется как новая операция. Сейчас импортируются только добавления, правки и удаления в Excel
в базу не переносятся.

Строки с некорректными данными (дата текстом, дробная или нулевая стоимость, пустые поля) пропускаются и
перечисляются в `skippedRows` результата синхронизации.

Надёжность:

- Одновременно идёт только один цикл. Запросы во время цикла объединяются в один следующий.
- Если файл изменили во время записи, цикл автоматически повторяется (один раз).
- Перед загрузкой записи помечаются `writing`. Если ответ о загрузке потерян, следующая сверка по
  содержимому Excel определяет, дошла ли запись, и не создаёт дубль.
- Если сделать резервную копию не удалось, Excel не меняется, записи остаются в очереди.

## API

Префикс `/api`, формат JSON.

| Метод и путь            | Назначение                                                              |
| ----------------------- | ----------------------------------------------------------------------- |
| `GET /api/health`       | Проверка работы, OneDrive не трогает                                    |
| `GET /api/config`       | Валюта                                                                  |
| `GET /api/cards`        | Список карт                                                             |
| `GET /api/categories`   | Категории: конфигурация + значения из базы (включая импортированные из Excel) |
| `POST /api/expenses`    | Добавить расход (нужен заголовок `Idempotency-Key`)                     |
| `GET /api/sync/status`  | Очередь, последний результат синхронизации, время следующего запуска    |
| `POST /api/sync`        | Запустить синхронизацию сейчас (если она уже идёт, присоединяется к ней) |

Пример:

```bash
curl -X POST localhost:3000/api/expenses -H 'content-type: application/json' \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"date":"2026-10-10","card":"Миша","category":"кафе","name":"Кофе","amount":1650}'
```

Успех — `201` (при повторе с тем же ключом — `200` и прежний результат):

```json
{ "success": true,
  "data": { "id": "…", "date": "2026-10-10", "card": "Миша", "category": "кафе", "name": "Кофе",
            "amount": 1650, "excelStatus": "synced" },
  "message": "Расход успешно добавлен" }
```

`excelStatus`: `synced` — расход уже в Excel; `queued` — сохранён в базе и ждёт записи в Excel.

`GET /api/sync/status` и `POST /api/sync` возвращают состояние:

```json
{ "success": true,
  "data": { "queued": 0, "running": false, "intervalMs": 300000,
            "nextRunAt": "2026-10-10T19:05:00.000Z", "serverTime": "2026-10-10T19:00:28.120Z",
            "lastResult": { "status": "ok", "imported": 3, "written": 1, "queued": 0,
                            "diverged": 0, "skipped": 0, "finishedAt": "…" } } }
```

`serverTime` нужен, чтобы таймер в интерфейсе шёл по часам сервера. Статус синхронизации (`lastResult.status`):
`ok`, `locked` (файл открыт в Excel), `unavailable` (OneDrive недоступен), `error`.

Ошибки: `{ "success": false, "error": { "code": "…", "message": "…" } }`

| Статус | Код                      | Когда                                                              |
| ------ | ------------------------ | ------------------------------------------------------------------ |
| 400    | `BAD_REQUEST`            | Битый JSON                                                         |
| 400    | `IDEMPOTENCY_KEY_REQUIRED`, `INVALID_IDEMPOTENCY_KEY` | Нет заголовка `Idempotency-Key` или он неверного формата |
| 422    | `INVALID_DATE`, `INVALID_CARD`, `INVALID_CATEGORY`, `INVALID_NAME`, `INVALID_AMOUNT` | Ошибка валидации |
| 422    | `IDEMPOTENCY_KEY_REUSED` | Ключ уже использован для другого расхода                           |
| 503    | `DATABASE_UNAVAILABLE`   | PostgreSQL недоступен; расход не сохранён, можно повторить         |
| 500    | `INTERNAL_ERROR`         | Внутренняя ошибка                                                  |

Недоступный Excel ошибкой **не является**: расход сохраняется, а ответ содержит `excelStatus: "queued"`.
Каждый ответ содержит заголовок `X-Request-Id` — тот же `requestId` стоит во всех строках лога запроса.

## Защита от дублей (Idempotency-Key)

`POST /api/expenses` требует заголовок `Idempotency-Key` (UUID). Ключ и расход сохраняются в одной
транзакции PostgreSQL, поэтому «неизвестного» состояния нет: либо сохранены оба, либо ни один.

| Ситуация                                       | Результат                                                         |
| ---------------------------------------------- | ----------------------------------------------------------------- |
| Новый ключ                                     | Расход создан, `201`                                              |
| Тот же ключ и те же данные                     | `200`, прежний результат (тот же `id`), нового расхода нет        |
| Одновременные запросы с одним ключом           | Расход создаётся один раз, остальные получают его результат       |
| Тот же ключ с другими данными                  | `422 IDEMPOTENCY_KEY_REUSED`                                      |
| Запрос не дошёл или ответ потерян (`503`, сеть) | Повторите с тем же ключом: безопасно                              |

Ключи старше `BACKUP_RETENTION_DAYS` дней удаляются.

## Режимы rclone и скорость

Каждый запуск rclone к OneDrive делает около шести последовательных HTTP-запросов, поэтому
отдельная команда занимает 4–5 секунд. Поэтому по умолчанию backend держит один постоянный
процесс `rclone rcd` (`RCLONE_MODE=daemon`), который переиспользует соединения:

| Режим    | Скачивание или загрузка файла (замер, Армения → OneDrive) |
| -------- | --------------------------------------------------------- |
| `daemon` | 1–3 секунды                                               |
| `cli`    | 5–9 секунд                                                |

Как работает режим `daemon`:

- backend сам запускает `rclone rcd`, а при остановке завершает его;
- процесс слушает только `127.0.0.1` на случайном порту, логин и пароль генерируются при каждом
  запуске и передаются через переменные окружения (в списке процессов не видны);
- если процесс упал, следующий запрос запускает его заново;
- если backend убит жёстко (`kill -9`), `rclone rcd` может остаться работать до перезагрузки;
  найти и остановить: `pkill -f "rclone rcd"`;
- если запрос завершился по таймауту, операция внутри rclone может ещё доработать до конца. Результат
  такой загрузки считается «неизвестным», и записи остаются в статусе `writing`, пока сверка не
  выяснит, попали ли они в Excel.

## Резервные копии

Перед каждым изменением Excel скачанный файл сохраняется в `BACKUP_DIR`:

```
backups/2026-10-10/expenses-20-15-32-a1b2c3.xlsx    # дата и время — по APP_TIMEZONE
```

- копия делается только когда в Excel что-то дописывается (одна копия на цикл, а не на расход);
- копии доступны только владельцу (папки `0700`, файлы `0600`) и не отдаются веб-сервером;
- при запуске и раз в сутки копии старше `BACKUP_RETENTION_DAYS` дней удаляются;
- копии лежат на том же диске, что и backend. Для надёжности периодически копируйте папку
  `backups/` в другое место. Сами расходы лежат ещё и в PostgreSQL, его бэкап делайте отдельно
  (`pg_dump`).

### Восстановление Excel из копии

```bash
./scripts/restore-backup.sh --list                      # какие копии есть
./scripts/restore-backup.sh backend/backups/2026-10-10/expenses-20-15-32-a1b2c3.xlsx
```

Скрипт проверяет, что копия — целая книга Excel, просит подтверждение (`yes`), сохраняет текущую
версию в `backups/before-restore/`, загружает копию в OneDrive и сверяет хеш. Перед запуском закройте
файл в Excel, иначе OneDrive откажет в записи.

**Важно: восстановление и база.** Записи, добавленные после момента копии, останутся в PostgreSQL, но
пропадут из Excel. Синхронизация покажет их как «есть в базе, но нет в Excel» и **не вернёт** в файл
автоматически. Данные при этом не потеряны: они в базе.

Также у файла есть история версий OneDrive (Excel или веб-интерфейс → «Журнал версий»).

## Логи

JSON-логи в stdout. На каждую операцию — строка с `requestId`, результатом и временем:

```json
{"requestId":"fa412ab2","operation":"expense.create","userId":"local","durationMs":3277,"result":"success","replayed":false,"excelStatus":"synced","msg":"Operation completed"}
{"operation":"sync","status":"ok","imported":0,"written":1,"queued":0,"diverged":0,"skipped":0,"msg":"Sync finished"}
```

Данные расхода (наименование, сумма), пароли и токены в лог не попадают; заголовки `Authorization`
и `Cookie` скрываются.

## Структура

```
src/
  app.ts, server.ts           сборка Fastify и запуск
  config/env.ts               переменные окружения
  modules/expenses/           маршруты, схема валидации, бизнес-логика
  modules/sync/               цикл синхронизации, сверка (reconcile), планировщик, маршруты
  storage/postgres/           репозиторий расходов (SQL)
  services/excel/             правка и чтение XLSX
  services/onedrive/          клиенты rclone (daemon и CLI), коды ошибок

```

Миграции — файлы `src/infrastructure/database/migrations/*.sql`, применяются при старте.

## Тесты

```bash
npm test                         # без обращения к OneDrive, без Docker
npm run typecheck
RUN_ONEDRIVE_TESTS=1 npm test    # + живые тесты с настоящим OneDrive (оба режима rclone, около 1,5 минуты)
```

Тесты PostgreSQL выполняются на PGlite — это настоящий PostgreSQL, собранный в WASM, поэтому Docker не
нужен. Драйвер `pg` проверяется отдельно по сетевому протоколу (`tests/integration/postgres-driver.test.ts`).

Живые тесты работают с отдельным файлом `Документы/expenses-tracker-test.xlsx` и удаляют его в конце;
рабочие файлы не затрагиваются.

Для интеграционных тестов нужна копия вашего Excel: `tests/fixtures/expenses-dev.xlsx`.
Файл содержит ваши данные и исключён из Git, поэтому после клонирования скачайте его сами:

```bash
mkdir -p tests/fixtures
rclone copyto "onedrive:Документы/Расходы-dev.xlsx" tests/fixtures/expenses-dev.xlsx
```

## Почему не ExcelJS для записи

При пересохранении ExcelJS теряет графики и динамические массивы из файла, поэтому запись выполняется
точечной правкой XML (`src/services/excel/`): меняются только лист и таблица, остальные части книги
остаются нетронутыми. ExcelJS используется только для чтения и проверки результата.
